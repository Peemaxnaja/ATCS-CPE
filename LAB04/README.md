## สรุปย่อ

README นี้ยาว ถ้าจะอ่านแค่ส่วนเดียวให้อ่านตรงนี้

1. คะแนน retrieval ที่ออกมาเกือบเต็มตอนแรกนั้นเชื่อไม่ได้ เพราะคำถามทดสอบถูกสร้างจาก dataset เอง เลยใช้คำชุดเดียวกัน ผมเขียนคำถามใหม่ด้วยมือ 55 ข้อโดยห้ามใช้คำเดิม แล้ว Hit@1 ร่วงจาก 0.99 เหลือ 0.64 ([รายละเอียด](#เขียนคำถามใหม่-55-ข้อ-แล้วภาพก็เปลี่ยน))
2. สมมติฐานของใบงานที่ว่า hybrid ควรชนะทุกวิธี เป็นจริงเฉพาะบนคำถามที่เขียนใหม่ ในสี่รูปแบบเดิม BM25 ล้วนชนะขาด
3. สิ่งที่ได้ผลมากที่สุดคือเปลี่ยนโมเดล embedding เป็น `multilingual-e5-small` dense MRR ขึ้นจาก 0.856 เป็น 0.936 ([รายละเอียด](#เปลี่ยนโมเดล-embedding--จุดที่ได้ผลมากที่สุดของใบงาน))
4. การปรับ RRF ตามที่ผมวิเคราะห์ไว้เองในรอบก่อน ลองแล้วไม่ช่วย วัด 4 ค่าไม่มีอันไหนชนะจริง
5. ระบบเดิมบอกว่า "ไม่รู้" ไม่เป็น ถามเรื่องส้มตำก็ตอบเรื่องปีกเดลตา เพิ่มเกณฑ์คะแนนแล้วปฏิเสธคำถามนอกเรื่องได้ 73.7% โดยไม่เผลอปฏิเสธคำถามที่ตอบได้เลย ([รายละเอียด](#ระบบเดิมบอกว่า-ไม่รู้-ไม่เป็นเลย))

ที่ยังทำไม่ได้คือส่วนที่ต้องใช้ LLM ได้แก่ reranking, query transformation และการให้ LLM เขียนคำตอบ เขียนโค้ดครบแล้วแต่เครื่องที่รันไม่มี LLM จึงยังพิสูจน์ไม่ได้

## งานที่ทำ

ต่อยอดจาก LAB02 ที่ทำ retrieval แบบ dense อย่างเดียว มาเป็นระบบ RAG เต็มรูป โดยเพิ่มของ Stage 2 เข้าไป คือ BM25 keyword search, การรวมอันดับด้วย RRF, cross-encoder reranking, query transformation, การให้ LLM เขียนคำตอบพร้อมอ้างอิง, ความจำบทสนทนา และที่สำคัญที่สุดคือ **ชุดวัดผล** ที่ทำให้ตอบได้ว่าแต่ละเทคนิคช่วยจริงหรือไม่ ด้วย Hit@k, Recall@k, Precision@k, MRR และ nDCG

ทุกฟีเจอร์เปิด-ปิดได้จาก `config.py` ตัวเดียว จุดประสงค์คือปิดทีละตัวแล้ววัดว่าคะแนนเปลี่ยนไปเท่าไร

หลังส่งรอบแรก ผมกลับมาทำต่อสี่เรื่องตามที่เขียนค้างไว้ในหัวข้อ "จะทำต่อยังไง" ได้แก่ เขียนคำถามทดสอบใหม่ด้วยมือ 55 ข้อ, แก้ชุดวัดผลให้ตรงกับระบบที่รันจริง, ลองปรับค่า RRF และเปลี่ยนโมเดล embedding — สองเรื่องหลังให้ผลตรงข้ามกับที่คาดไว้ สรุปทั้งสี่เรื่องอยู่ท้าย README

knowledge base เป็นชุดถาม-ตอบความรู้ทางทหารที่ผมทำขึ้นเอง 361 คู่ อยู่ที่ `data/military_qa.txt`

ขอบเขตของข้อมูลคือ **ความรู้เชิงสารานุกรม** เท่านั้น — การจำแนกประเภท หลักการทำงาน ประวัติ และคำศัพท์ ไม่มีข้อมูลเชิงปฏิบัติการ วิธีสร้างหรือดัดแปลงอาวุธ ตัวเลขสมรรถนะทั้งหมดเป็นค่าโดยประมาณจากแหล่งข้อมูลสาธารณะ ระบบขึ้น disclaimer นี้ท้ายคำตอบทุกครั้ง

ข้อความเขียนขึ้นใหม่ทั้งหมด ไม่ได้คัดลอกประโยคจากที่ใด แต่ข้อเท็จจริงในนั้นเป็นความรู้มาตรฐานของโดเมน จึงมีตารางบอกแหล่งตรวจสอบรายหมวดไว้ที่หัวข้อ [แหล่งตรวจสอบข้อเท็จจริงใน dataset](#แหล่งตรวจสอบข้อเท็จจริงใน-dataset)

### สิ่งที่แก้จากโครงร่างต้นฉบับ

skeleton ที่อาจารย์ให้มาผูกกับโดเมนสุขภาพทางเพศไว้หลายจุด ผมเปลี่ยนทั้งหมดมาเป็นโดเมนทหาร ได้แก่ `SYSTEM_PROMPT`, `REWRITE_PROMPT`, `MULTI_QUERY_PROMPT`, `HYDE_PROMPT`, ตาราง `SLANG_MAP` ใน `query_transform.py`, ตาราง `TO_SLANG` ใน `build_golden_set.py` และคำถามตัวอย่างใน `lab07`

นอกจากเปลี่ยนโดเมนแล้ว มีสามจุดที่เป็นบั๊กจริงและต้องแก้

**หนึ่ง — โหมดไม่ใช้ LLM ตอบว่า "ไม่พบข้อมูล" ทุกครั้ง**

`NoLLM.chat()` ตัดข้อความบริบทออกจาก prompt ด้วยการ split ที่สตริง `"reference data :"` และ `"Q of user"` แต่ `USER_PROMPT` ในไฟล์เดียวกันเขียนหัวข้อไว้เป็นภาษาไทยว่า `"ข้อมูลอ้างอิง:"` และ `"คำถามของผู้ใช้:"` ทั้งสองสตริงจึงไม่มีทางเจอ ฟังก์ชันเลยคืน `NO_CONTEXT_MESSAGE` เสมอ ทั้งที่ retriever ค้นเจอเอกสารมาแล้ว

ผมย้ายหัวข้อทั้งสองออกมาเป็นค่าคงที่ `CONTEXT_HEADER` / `QUESTION_HEADER` ใน `prompt_templates.py` แล้วให้ `generator.py` import ไปใช้ ต่อไปแก้ prompt แล้วโหมดนี้จะไม่หลุดอีก เพราะไม่มีใครเดาสตริงเอง

จุดนี้สำคัญกับงานนี้เป็นพิเศษ เพราะเครื่องที่ผมรันไม่มี LLM ให้ใช้ ทั้งใบงานจึงต้องรันด้วย `USE_LLM = False` ถ้าไม่แก้ ผลวัดคำตอบจะออกมาว่าระบบปฏิเสธ 100%

**สอง — golden set สร้าง variant "partial" ให้ภาษาไทยแทบไม่ได้เลย**

`make_variants()` ตัดคำด้วย `re.split(r"[\s()/]+", ...)` ซึ่งอาศัยช่องว่าง คำถามภาษาไทยล้วนจึงถูกนับเป็นก้อนเดียว ไม่ผ่านเงื่อนไข `len(words) >= 2` ตอนทดสอบครั้งแรกด้วย dataset 182 คู่ สร้าง partial ได้แค่ 20 จาก 60 ข้อ เฉพาะข้อที่บังเอิญมีชื่อรุ่นภาษาอังกฤษคั่นอยู่อย่าง `AK-47` หรือ `S-400`

ผมเปลี่ยนมาตัดคำไทยด้วย pythainlp (engine `newmm`) แบบเดียวกับที่ BM25 ใช้อยู่แล้ว แยกออกมาเป็นฟังก์ชัน `content_words()` และเพิ่มคำเชื่อมไทยเข้า `STOPWORDS` เพราะพอตัดคำจริงแล้ว คำอย่าง "กับ" "จาก" "โดย" โผล่ขึ้นมาเต็มไปหมด ตอนนี้สร้าง partial ได้ครบทุกข้อ

**สาม — `SHOW_SOURCES` เปิดไว้แต่โค้ดที่แสดงผลถูก comment ทิ้ง**

ใน `main.py` บล็อกที่พิมพ์รายการแหล่งอ้างอิงถูก comment ไว้ทั้งก้อน ตั้งค่ายังไงก็ไม่แสดง ผมเปิดกลับมาและแปลข้อความเป็นไทย เพราะใบงานนี้ต้องตรวจสอบย้อนกลับได้ว่าเลข `[1]` ในคำตอบมาจากคู่ Q&A ไหน บรรทัดที่เท่าไรของไฟล์ต้นฉบับ

ค่าเริ่มต้นอื่นที่เปลี่ยน — `USE_LLM = False` (ให้ clone มาแล้วรันได้เลยโดยไม่ต้องมี Ollama), `SOURCE_FILE` ชี้ไป `military_qa.txt` และ `GOLDEN_SET_SIZE` ขยายจาก 60 เป็น 120 ให้สอดคล้องกับ dataset ที่โตขึ้น

## ชุดข้อมูล

รูปแบบเดียวกับ LAB02 คือ `[หมวด]` / `Q:` / `A:` คั่นแต่ละคู่ด้วยบรรทัดว่าง เขียนใหม่ทั้งหมด 361 คู่ กระจาย 12 หมวดให้เท่ากันหมวดละ 30 ข้อ เพื่อไม่ให้หมวดใหญ่กินพื้นที่ตอนสุ่ม golden set

| หมวด | จำนวน Q&A |
| :--- | :---: |
| อาวุธปืนเล็ก | 30 |
| ปืนใหญ่และอาวุธสนับสนุน | 31 |
| รถถังและยานเกราะ | 30 |
| อากาศยานรบ | 30 |
| เฮลิคอปเตอร์ทางทหาร | 30 |
| เรือรบและเรือดำน้ำ | 30 |
| ขีปนาวุธและการป้องกันภัยทางอากาศ | 30 |
| อากาศยานไร้คนขับและสงครามอิเล็กทรอนิกส์ | 30 |
| กองทัพไทย | 30 |
| หลักนิยมและคำศัพท์ทางทหาร | 30 |
| สงครามไซเบอร์และปฏิบัติการอวกาศ | 30 |
| อาวุธนิวเคลียร์และการควบคุมอาวุธ | 30 |
| **รวม** | **361** |

คำตอบยาวเฉลี่ย 286 ตัวอักษร ยาวสุด 363 ที่ `CHUNK_SIZE = 400` จึงมีแค่ 3 ข้อที่ถูกตัดเป็น 2 ชิ้น รวมได้ 364 chunks — ต่างจาก LAB02 ที่ 313 คู่แตกเป็น 419 chunks เพราะคราวนี้ผมคุมความยาวคำตอบไว้ตั้งแต่ตอนเขียน dataset

ผมทำ dataset สองรอบ รอบแรก 182 คู่ (หมวดละ 15) แล้วขยายเป็น 361 คู่ในรอบที่สอง การได้วัดผลทั้งสองรอบด้วยโค้ดชุดเดียวกันกลายเป็นข้อมูลที่มีประโยชน์ที่สุดของใบงานนี้ — อธิบายไว้ในหัวข้อผลการทดลอง

## สถาปัตยกรรม

```
data/military_qa.txt
       │
       ▼  document_loader.py                361 Q&A + category + line_no
outputs/extracted_text.json
       │
       ▼  text_splitter.py                  CHUNK_SIZE=400, OVERLAP=50
outputs/chunks.json                         364 chunks
       │
       ├──► embedding_model.py              paraphrase-multilingual-MiniLM-L12-v2
       │    outputs/embeddings.npy          (364, 384) float32, L2-normalized
       │         │
       │         ▼  vector_store.py         FAISS IndexFlatIP
       │    vector_db/document.index
       │
       └──► hybrid_retriever.build_bm25()   tokenize ไทยด้วย pythainlp newmm
            vector_db/bm25_index.pkl        คำถามถูกใส่ซ้ำ 2 ครั้งใน corpus

─────────────────────────── ตอบคำถาม ───────────────────────────

query
  │
  ▼  query_transform.py     normalize_query() แทนคำพูด → ศัพท์ทางทหาร
  │                         (ถ้าเปิด USE_QUERY_TRANSFORM จะเรียก LLM
  │                          ทำ rewrite / multi_query / hyde เพิ่ม)
  ├──────────────┬──────────────┐
  ▼              ▼              │  ค้นทุกคำถามที่แปลงได้ ทุกวิธี
dense search   BM25 search      │  CANDIDATE_K = 20
  │              │              │
  └──────┬───────┘              │
         ▼  reciprocal_rank_fusion()   score = Σ 1/(RRF_K + rank)
         │
         ▼  rerankers.py        cross-encoder จัดอันดับใหม่ (ถ้าเปิด USE_RERANK)
         │
         ▼  rag_pipeline.is_in_scope()   คะแนน dense ดีสุด < MIN_DENSE_SCORE ?
         │                               ถ้าใช่ ทิ้ง chunk ทั้งหมด → ตอบว่าไม่รู้
         │
         ▼  prompt_templates.format_context()   บล็อก [1] [2] [3]
         │
         ▼  generator.py        LLM เขียนคำตอบ + อ้างอิง [n]
         │                      ถ้า USE_LLM = False → คืนบล็อก [1] ตรง ๆ
         ▼
      คำตอบ + แหล่งอ้างอิง + disclaimer
         │
         ▼  memory.py           เก็บ MEMORY_MAX_TURNS = 6 รอบล่าสุด
```

เวกเตอร์ถูก normalize มาตั้งแต่ขั้น embedding การใช้ `IndexFlatIP` จึงเท่ากับ cosine similarity เหมือน LAB02

จุดที่ต่างจาก LAB02 อย่างมีนัยคือ **RRF ไม่ได้เอาคะแนนดิบมาบวกกัน แต่บวกจากอันดับ** (`1/(60 + rank)`) เพราะคะแนน cosine กับคะแนน BM25 อยู่คนละสเกล เทียบกันตรง ๆ ไม่ได้ ผลข้างเคียงคือคะแนนที่แสดงในโหมด hybrid จะอยู่ราว 0.03 ไม่ใช่ 0.7-0.8 แบบ dense ล้วน

## ผลการทดลอง

### ชุดวัดผล

`build_golden_set.py` สุ่ม 120 ข้อจาก 364 chunks แบบกระจายหมวดละ 10 ข้อ แล้วแปลงคำถามต้นฉบับเป็นหลายรูปแบบ เพื่อดูว่าระบบทนคำถามที่ไม่ตรงตัวได้แค่ไหน

| รูปแบบ | คืออะไร | จำนวนที่สร้างได้ | ตัวอย่าง |
| :--- | :--- | :---: | :--- |
| `verbatim` | คำถามต้นฉบับ ใช้ดูเพดานบนของระบบ | 120 | ปืนกลเอนกประสงค์คืออะไร มีตัวอย่างอะไรบ้าง |
| `slang` | แทนศัพท์ทางทหารด้วยภาษาพูด | 26 | รถถัง → แทงค์, เฮลิคอปเตอร์ → ฮ., เรือดำน้ำ → ซับมารีน |
| `partial` | ตัดเหลือแต่คำเนื้อหา แบบที่คนพิมพ์ค้นจริง | 120 | ปืนกล เอนกประสงค์ |
| `natural` | เติมคำนำ/คำลงท้ายแบบภาษาพูด | 120 | สงสัยว่าปืนกลเอนกประสงค์คืออะไร มีตัวอย่างอะไรบ้าง ยังไงคะ |
| `paraphrase` | **ผมเขียนเองด้วยมือ ห้ามใช้คำเนื้อหาชุดเดิม** | 55 | ทำไมยานเกราะสายพานถึงเสี่ยงกว่าเดิมมากในสงครามยุคนี้ (จาก "โดรนเปลี่ยนบทบาทของรถถังอย่างไร") |

`slang` สร้างได้ 26 ข้อ เพราะเงื่อนไขคือคำถามต้องมีคำในตาราง `TO_SLANG` อยู่จริง

`paraphrase` เป็นรูปแบบที่เพิ่มมาทีหลัง และเป็นรูปแบบเดียวที่ไม่ได้สร้างจากคำถามต้นฉบับ — เหตุผลอยู่ในหัวข้อถัดไป ผมเขียนไว้ 55 ข้อ กระจายครบทั้ง 12 หมวด เก็บไว้ที่ [`data/paraphrases.json`](RAG-Project/data/paraphrases.json) แยกจาก `golden_set.json` เพราะสร้าง golden set ใหม่กี่รอบก็ต้องไม่หาย

### สิ่งที่เห็นเมื่อ dataset โตขึ้นสองเท่า

ผมรันชุดวัดผลเดียวกันตอน dataset มี 182 คู่ (184 chunks) แล้วรันซ้ำตอนขยายเป็น 361 คู่ (364 chunks) ผลต่างชัดมาก

ตัวเลขในตารางนี้วัดด้วย **4 variant เดิม และยังไม่ผ่าน `normalize_query()`** ทั้งสองรอบ จึงไม่ตรงกับตารางภาพรวมข้างบนที่เพิ่ม `paraphrase` เข้ามาแล้ว ที่ต้องทำแบบนี้เพราะรอบ 182 คู่ยังไม่มีทั้งสองอย่าง ถ้าเอาตัวเลขคนละเงื่อนไขมาเทียบกันก็ไม่ได้วัดผลของขนาดคลังอีกต่อไป

| วิธีค้น | MRR ที่ 184 chunks | MRR ที่ 364 chunks | เปลี่ยนแปลง |
| :--- | :---: | :---: | :---: |
| dense_only | 0.9336 | 0.8803 | −5.7% |
| bm25_only | 0.9965 | 0.9821 | −1.4% |
| hybrid (RRF) | 0.9765 | 0.9426 | −3.5% |

ทุกวิธีตกลงเมื่อคลังใหญ่ขึ้น ซึ่งเป็นเรื่องปกติเพราะมีตัวเลือกให้สับสนมากขึ้น แต่ **dense ตกแรงที่สุด** และรูปแบบ `slang` ตกจาก 0.9000 เหลือ 0.6934

ข้อสรุปที่ได้คือตัวเลขจากคลังเล็กหลอกตาได้ง่าย ตอน 184 chunks ทุกวิธีอยู่เหนือ 0.93 หมดจนแทบแยกไม่ออกว่าอะไรดีกว่าอะไร พอคลังโตขึ้นเท่าตัว ช่องว่างระหว่าง dense กับ BM25 จึงเปิดออกให้เห็น การรายงานคะแนน retrieval โดยไม่บอกขนาดคลังจึงแทบไม่มีความหมาย

### ผลออกมาไม่ตรงกับที่ใบงานคาด

สมมติฐานที่ใบงานตั้งไว้คือ hybrid ควรชนะทุกวิธี แต่ผลจริงคือ **BM25 ล้วนชนะขาด** ทั้งแม่นกว่าและเร็วกว่า dense หกเท่า ส่วน hybrid อยู่ตรงกลาง คือถูกฉุดลงมาจาก BM25

ก่อนจะสรุปว่า BM25 ดีกว่า ต้องบอกก่อนว่าตัวเลขชุดนี้ยัง **สูงเกินจริง** เพราะ golden set สร้างจากคำถามใน dataset เอง

- `verbatim` คือคำถามต้นฉบับเป๊ะ ๆ → BM25 จับคำได้ 100% เป็นธรรมดา
- `natural` แค่เติม "สงสัยว่า" ข้างหน้าและ "คะ" ข้างหลัง เนื้อคำถามยังเหมือนเดิมทุกตัวอักษร → คะแนนจึงเกือบเท่ากับ verbatim
- `partial` คือคำที่ตัดมาจากคำถามเดิม ก็ยังเป็นคำเดิมอยู่ดี

แปลว่าสามในสี่รูปแบบวัด "การจับคำตรงตัว" มากกว่าวัดความเข้าใจความหมาย งานนี้จึงเข้าทาง BM25 ตั้งแต่ต้น ถ้าจะวัดของจริงต้องมีคำถามที่ **เขียนใหม่ด้วยคำคนละชุด**

### เขียนคำถามใหม่ 55 ข้อ แล้วภาพก็เปลี่ยน

ผมเลยนั่งเขียนคำถามเองด้วยมือ 55 ข้อ กระจายครบ 12 หมวด กติกาข้อเดียวคือ **ห้ามใช้คำเนื้อหาชุดเดียวกับคำถามต้นฉบับ** ถ้าต้นฉบับเรียกชื่อสิ่งของ ผมจะถามด้วยลักษณะของมันแทน

```

ต้นฉบับ   ระวางขับน้ำของเรือรบหมายถึงอะไร

```

พอวัดด้วยชุดนี้ ตัวเลขทั้งชุดตกลงมาอยู่ในระดับที่เชื่อได้

| วิธีค้น | Hit@1 | Hit@10 | MRR | nDCG@3 |
| :--- | :---: | :---: | :---: | :---: |
| dense_only | 0.4364 | 0.8364 | 0.5815 | 0.5965 |
| bm25_only | 0.5818 | 0.8000 | 0.6494 | 0.6459 |
| **hybrid (RRF)** | **0.6364** | **0.9455** | **0.7094** | **0.6775** |

สามอย่างที่เห็นจากตารางนี้

**หนึ่ง — Hit@1 ร่วงจาก 0.99 เหลือ 0.64** ตัวเลขเกือบเต็มในตารางหลักไม่ได้แปลว่าระบบเก่ง แต่แปลว่าข้อสอบง่ายเกินไป พอเปลี่ยนมาถามด้วยคำคนละชุด ระบบเลือกอันดับ 1 ผิดถึงหนึ่งในสามของคำถาม

**สอง — hybrid ชนะทั้งสองวิธีที่เอามารวมเป็นครั้งแรก** ในสี่รูปแบบเดิม hybrid แพ้ BM25 ตลอด แต่พอไม่มีคำให้จับตรง ๆ แล้ว การรวมสองวิธีถึงคุ้ม เหตุผลที่ใบงานยกมาว่าทำไมต้องทำ hybrid เพิ่งจะพิสูจน์ได้ตรงนี้เอง

**สาม — BM25 มี Hit@10 ต่ำที่สุด (0.8000) ต่ำกว่า dense ด้วยซ้ำ** แปลว่าเวลา BM25 พลาด มันพลาดหมดเลย ไม่ได้แค่จัดอันดับสลับ ส่วน dense ยังพอค้นเจอในอันดับท้าย ๆ พอเอามารวมกัน hybrid จึงได้ Hit@10 ถึง 0.9455 — ของถูกที่ dense หามาได้ถูก BM25 ดันขึ้นมา

ข้อสรุปคือ **ชุดวัดผลที่สร้างอัตโนมัติจาก dataset จะเอียงเข้าทาง keyword search เสมอ** ต่อให้แปลงคำถามกี่รูปแบบก็ตาม ตราบใดที่ยังแปลงมาจากคำถามเดิม

คำถาม 55 ข้อนี้ใช้เวลาเขียนไม่ถึงชั่วโมง แต่เปลี่ยนข้อสรุปของทั้งใบงาน

### ทำไม dense ถึงพังตอนเจอ partial และ slang

ในรูปแบบ `partial` dense เลือกอันดับ 1 ผิด 45 ข้อจาก 120 ลองดูของจริง

```
g0006  "ปืน ซุ่ม ยิง ปืน"          (จาก "ปืนซุ่มยิงกับปืนต่อต้านยุทโธปกรณ์ต่างกันอย่างไร")
       ควรได้ [6]
       dense  [40, 27, 50]   อันดับ 1 = อาวุธนำวิถีต่อสู้รถถังแบบ fire-and-forget คืออะไร
       bm25   [6, 23, 41]    ถูกตั้งแต่อันดับ 1

g0022  "ปืนกล เบา ต่าง"           (จาก "ปืนกลเบาต่างจากปืนกลเอนกประสงค์อย่างไร")
       ควรได้ [22]
       dense  [40, 11, 215]  อันดับ 1 = อาวุธนำวิถีต่อสู้รถถังแบบ fire-and-forget คืออะไร
       bm25   [22, 133, 9]

g0026  "ระบบ ราง"                 (จาก "ระบบราง Picatinny คืออะไร")
       ควรได้ [26]
       dense  [162, 210, 26] อันดับ 1 = ตอร์ปิโดสมัยใหม่นำวิถีอย่างไร
       bm25   [26, 117, 89]
```

chunk `[40]` โผล่เป็นอันดับ 1 ที่ผิดซ้ำ ๆ ในคำถามคนละหมวดกันเลย ทั้งปืนซุ่มยิงและปืนกลเบา ปรากฏการณ์นี้เรียกว่า hub vector — เวกเตอร์ที่บังเอิญอยู่กลาง ๆ ของ embedding space แล้วกลายเป็นเพื่อนบ้านที่ใกล้ที่สุดของ query ที่โมเดลอ่านไม่ออก ในรอบนี้มี hub หลายตัว ได้แก่ `[40]`, `[126]` และ `[321]` ตัวละ 3 ครั้ง

สาเหตุที่โมเดลอ่านไม่ออกคือรูปแบบข้อความ `partial` เอาคำที่ตัดแล้วมาต่อกันด้วยช่องว่าง `"ปืนกล เบา ต่าง"` ซึ่งไม่ใช่ประโยคภาษาไทยที่ `paraphrase-multilingual-MiniLM-L12-v2` เคยเห็นตอนเทรน พอ encode ออกมาเวกเตอร์เลยไม่มีทิศทางชัดเจน แล้วตกไปหา hub ส่วน BM25 ไม่สนใจเรื่องนี้เลย เพราะมันตัดคำใหม่แล้วนับคำตรง ๆ ช่องว่างจึงไม่มีผล

ส่วนรูปแบบ `slang` เป็นคนละสาเหตุ ตัวอย่างชัดที่สุดคือคำย่อ

```
g0126  "ฮ.ปราบซับมารีนทำงานอย่างไร"   (จาก "เฮลิคอปเตอร์ปราบเรือดำน้ำทำงานอย่างไร")
       ควรได้ [127]
       dense  [162, 43, 172]  อันดับ 1 = ตอร์ปิโดสมัยใหม่นำวิถีอย่างไร
       bm25   [127, 38, 16]

g0183  "มิสไซล์อากาศสู่อากาศนำวิถีอย่างไร"  (จาก "ขีปนาวุธอากาศสู่อากาศนำวิถีอย่างไร")
       ควรได้ [184]
       dense  [126, 121, 100] อันดับ 1 = การบินแบบ nap-of-the-earth คืออะไร
       bm25   [184, 200, 146]
```

น่าสนใจว่า BM25 กลับตอบถูกทั้งที่ `ฮ.` กับ `เฮลิคอปเตอร์` ไม่ใช่คำเดียวกัน สาเหตุคือคำที่เหลือในประโยคอย่าง "ปราบ" และ "อากาศสู่อากาศ" ยังตรงกับเอกสารพอดี ขณะที่ dense เอาทั้งประโยครวมเป็นเวกเตอร์เดียว คำย่อที่ไม่รู้จักจึงบิดทิศทางของทั้งประโยค

### ตาราง SLANG_MAP ใช้ได้ผล และตอนนี้ชุดวัดผลเรียกมันแล้ว

เดิม `eval_retrieval.py` เรียก `retriever.retrieve()` ตรง ๆ ไม่ผ่าน `RAGPipeline` ฟังก์ชัน `normalize_query()` ที่แทนคำพูดด้วยศัพท์ทางทหารจึงไม่เคยถูกเรียก **ตัวเลขที่วัดได้เป็นของระบบคนละตัวกับที่ `main.py` รันจริง**

ผมแก้ให้ทุกแถวเดินผ่าน `normalize_query()` แล้ว และเก็บแถว `hybrid_raw` ไว้เทียบให้เห็นว่าขั้นนี้ให้อะไร

| วิธีค้น (เฉพาะ 26 ข้อ slang) | MRR ดิบ | MRR หลัง normalize | เปลี่ยนแปลง |
| :--- | :---: | :---: | :---: |
| dense_only | 0.6934 | 0.9286 | **+33.9%** |
| hybrid (RRF) | 0.8465 | 0.9551 | +12.8% |

ตารางแทนคำพูด 11 บรรทัดที่ไม่ใช้ AI เลย กู้คะแนน dense กลับมาได้เกือบทั้งหมด และผลนี้จำกัดอยู่ที่ `slang` เท่านั้น — อีกสี่รูปแบบไม่ขยับเลยแม้แต่ทศนิยมตำแหน่งที่สี่ ซึ่งก็ถูกแล้ว เพราะไม่มีคำไหนในนั้นตรงกับตาราง

บทเรียนที่ได้จริง ๆ ไม่ใช่เรื่อง normalize แต่เป็นเรื่อง **ชุดวัดผลกับระบบที่ใช้งานต้องเป็นตัวเดียวกัน** ถ้าไม่แก้ ผมจะรายงานคะแนน `slang` ต่ำกว่าความจริงไปเรื่อย ๆ โดยไม่รู้ตัว

### RRF ทำให้แย่ลงได้ ถ้าสัญญาณฝั่งหนึ่งเสีย

hybrid **แพ้ BM25 ล้วน** ทุกรูปแบบคำถาม และมีเคสที่ hybrid ทำผลเสียกว่าทั้งสองวิธีที่เอามารวมกัน — ในรูปแบบ `partial` มี 6 เคส และในรูปแบบ `slang` มี 3 เคส ที่ BM25 ได้คำตอบถูกตั้งแต่อันดับ 1 แต่พอรวมกับ dense แล้วคำตอบที่ถูกหลุด top-3 ไปเลย

```
g0199  "ขีปนาวุธ อากาศ สู่ อากาศ"
       ควรได้ [200]
       dense  [126, 121, 162]  ผิดทั้งสามอันดับ
       bm25   [200, 184, 201]  ถูกตั้งแต่อันดับ 1
       hybrid [130, 300, 184]  ผิดทั้งสามอันดับ

g0126  "ฮ.ปราบซับมารีนทำงานอย่างไร"
       ควรได้ [127]
       dense  [162, 43, 172]   ผิด
       bm25   [127, 38, 16]    ถูกอันดับ 1
       hybrid [38, 83, 194]    ผิด
```

RRF ให้คะแนนจากอันดับ `1/(60 + rank)` โดยเชื่อทั้งสองฝั่งเท่ากัน ไม่มีกลไกดูว่าฝั่งไหนมั่นใจแค่ไหน พอ dense เดามั่วมาทั้งลิสต์ คะแนนขยะจากฝั่งนั้นก็ยังถูกบวกเข้าไปเต็ม ๆ และเนื่องจากผู้เข้ารอบจาก dense มี 20 ตัว ขณะที่ของถูกจาก BM25 มีตัวเดียว ผลรวมจึงถูกเสียงข้างมากที่ผิดกลบ

บทเรียนคือ hybrid ไม่ใช่ของที่เปิดแล้วดีขึ้นเสมอ มันดีขึ้นต่อเมื่อสองวิธีผิดคนละแบบ ถ้าวิธีหนึ่งผิดแบบสุ่มทั้งลิสต์ การเอามารวมคือการเจือจางของดี

### ลองแก้ RRF ตามที่วิเคราะห์ไว้ แล้วมันไม่ช่วย

คำอธิบายข้างบนฟังดูเข้าท่า ผมเลยลองแก้ตามนั้นจริง เพิ่มสองอย่างเข้า `hybrid_retriever.py` — ถ่วงน้ำหนักแต่ละฝั่งแทนที่จะเชื่อเท่ากัน และตัดผู้เข้ารอบที่คะแนนต่ำกว่าอันดับ 1 เกินกำหนดทิ้งก่อนเข้า fusion (ฟังก์ชัน `prune()`) ค่า floor เป็นสัดส่วนไม่ใช่ค่าคงที่ เพราะคะแนน cosine กับ BM25 อยู่คนละสเกล

วัดบน `paraphrase` อย่างเดียว เพราะอีกสี่รูปแบบเกาะ 1.0 อยู่แล้ว ปรับอะไรก็ไม่ขยับ ([`eval_rrf_settings.py`](RAG-Project/evaluation/eval_rrf_settings.py))

| ค่าที่ลอง | Hit@1 | Hit@10 | MRR | nDCG@3 |
| :--- | :---: | :---: | :---: | :---: |
| ค่าเดิม (เชื่อเท่ากัน ไม่ตัด) | 0.6364 | 0.9455 | 0.7094 | 0.6775 |
| เชื่อ BM25 น้อยลง (×0.5) | 0.6000 | 0.8909 | 0.6884 | 0.6846 |
| เชื่อ BM25 มากขึ้น (×2.0) | 0.6364 | 0.8545 | 0.6976 | 0.6799 |
| ตัดตัวคะแนนต่ำทิ้ง (floor 0.8) | 0.6364 | 0.9455 | **0.7160** | 0.6981 |

**ไม่มีอันไหนชนะจริง** การถ่วงน้ำหนักทำให้แย่ลงทั้งสองทิศทาง แปลว่าการเชื่อสองฝั่งเท่ากันเป็นค่าที่ดีอยู่แล้ว ส่วนการตัดตัวคะแนนต่ำได้ MRR +0.9% โดย Hit@1 ไม่ขยับเลย บนคำถาม 55 ข้อ ส่วนต่างขนาดนี้บอกอะไรไม่ได้ ผมจึง **ปล่อยค่าเริ่มต้นไว้เหมือนเดิม** และเก็บสวิตช์ทั้งสองไว้ในโค้ดเพื่อให้รันซ้ำได้

ที่ควรบันทึกไว้คือคำอธิบายเรื่อง "ขยะ 20 ตัวมาโหวต" อธิบายเคสที่ยกมาข้างบนได้ดี แต่พอลองแก้ตามแล้วคะแนนรวมไม่ขยับ แปลว่ามันไม่ใช่สาเหตุหลัก การมีเหตุผลที่ฟังขึ้นกับการมีหลักฐานเป็นคนละเรื่องกัน

### เปลี่ยนโมเดล embedding — จุดที่ได้ผลมากที่สุดของใบงาน

อาการ hub vector ที่เจอในใบงานนี้ ผมเจอแบบเดียวกันมาแล้วใน LAB02 ซึ่งใช้โมเดลตัวเดียวกัน จุดร่วมชัดพอที่จะสงสัยตัวโมเดล ไม่ใช่ตัวข้อมูล

`paraphrase-multilingual-MiniLM-L12-v2` เทรนมาเพื่อวัดความคล้ายของประโยคทั่วไป ไม่ได้เทรนมาเพื่องานค้นหา ส่วน `intfloat/multilingual-e5-small` มีขนาดเวกเตอร์เท่ากันคือ 384 มิติ แต่เทรนด้วยคู่ query/passage ซึ่งตรงกับงานที่เราใช้มันทำ

เทียบด้วย [`compare_embedders.py`](RAG-Project/evaluation/compare_embedders.py) โดย **ตรึงทุกอย่างให้เหมือนกัน** — chunk ชุดเดียวกัน ลำดับเดียวกัน BM25 index ตัวเดียวกัน golden set ชุดเดียวกัน เปลี่ยนแค่ FAISS index ส่วนต่างที่เห็นจึงเป็นของ embedder ล้วน

**dense อย่างเดียว**

| โมเดล | Hit@1 | Hit@10 | MRR | nDCG@3 |
| :--- | :---: | :---: | :---: | :---: |
| MiniLM | 0.8005 | 0.9546 | 0.8557 | 0.8592 |
| **e5-small** | **0.9093** | **0.9864** | **0.9364** | **0.9377** |

**hybrid**

| โมเดล | Hit@1 | Hit@10 | MRR | nDCG@3 |
| :--- | :---: | :---: | :---: | :---: |
| MiniLM | 0.8866 | 0.9932 | 0.9196 | 0.9151 |
| **e5-small** | **0.9274** | 0.9909 | **0.9493** | **0.9465** |

**dense MRR แยกตามรูปแบบคำถาม** — ช่องว่างกว้างที่สุดตรงที่ MiniLM อ่อนที่สุดพอดี

| โมเดล | verbatim | slang | partial | natural | paraphrase |
| :--- | :---: | :---: | :---: | :---: | :---: |
| MiniLM | 0.9748 | 0.9286 | 0.7235 | 0.9788 | 0.5815 |
| e5-small | 1.0000 | **1.0000** | **0.9182** | 1.0000 | **0.6688** |

`partial` คือรูปแบบที่ MiniLM ตกไปหา hub vector — e5 ทำได้ 0.9182 จาก 0.7235 ส่วน `slang` e5 ได้เต็ม 1.0000 **โดยไม่ต้องพึ่งตาราง `SLANG_MAP` เลย** คือมันรู้เองว่า "แทงค์" กับ "รถถัง" คือของเดียวกัน

ทั้งสองโมเดลมี 384 มิติเท่ากัน เรื่องนี้จึงไม่เกี่ยวกับขนาด แต่เกี่ยวกับว่าเทรนมาทำอะไร

สองข้อที่ต้องบอกไว้ด้วย

**หนึ่ง — e5 ต้องเติมคำนำหน้า** `query: ` ฝั่งคำถาม และ `passage: ` ฝั่งเอกสาร ถ้าลืมเติม โมเดลยังคืนเวกเตอร์ให้ตามปกติ แค่คุณภาพแย่ลงเงียบ ๆ ไม่มี error ให้เห็น ผมเลยเก็บค่านี้ไว้ใน `config.py` ติดกับชื่อโมเดลเลย

**สอง — บน `paraphrase` ส่วนต่างเล็กกว่ามาก** hybrid ขยับจาก 0.7094 เป็น 0.7241 เท่านั้น แปลว่าคำถามที่ยากจริงยังยากสำหรับทั้งสองโมเดล การเปลี่ยน embedder แก้ปัญหา hub vector ได้ แต่ไม่ได้ทำให้ระบบเข้าใจคำถามที่เขียนใหม่ทั้งประโยค

ผมยัง **ไม่เปลี่ยนค่าเริ่มต้นใน `config.py`** เป็น e5 เพราะจะทำให้ตัวเลขทุกตารางข้างบนเทียบกับรอบก่อนไม่ได้ แต่ถ้าจะเอาไปใช้จริงควรเปลี่ยน วิธีสลับอยู่ในหัวข้อวิธีรัน

### คุณภาพคำตอบ — ยังวัดไม่ได้จริง

`eval_generation.py` รัน 20 ข้อ ผลอยู่ใน [`outputs/eval_generation.json`](RAG-Project/outputs/eval_generation.json)

เดิมไฟล์นี้ใช้คำถามรูปแบบ `natural` ซึ่งเป็นรูปแบบที่ retriever ค้นถูกเกือบทุกข้ออยู่แล้ว (MRR 0.99) การเอาคำถามที่ระบบตอบถูกแน่ ๆ มาวัดคุณภาพคำตอบจึงไม่ได้บอกอะไร ผมเปลี่ยนมาใช้ `paraphrase` แทน

| ตัวชี้วัด | ใช้ `natural` (เดิม) | ใช้ `paraphrase` |
| :--- | :---: | :---: |
| อัตราการตอบว่าไม่รู้ | 0.0 | 0.0 |
| **อัตราค้นเจอ chunk ที่ถูก** | 1.0 | **0.6** |
| มีการอ้างอิง `[n]` | 1.0 | 1.0 |
| faithfulness | 1.0 | 1.0 |
| **correctness** | 0.9804 | **0.6538** |
| relevance | 0.4109 | 0.3327 |
| เวลาเฉลี่ย | 0.051 วินาที | 0.050 วินาที |

**ตัวเลขชุดนี้อ่านตามตัวไม่ได้** เพราะเครื่องที่ผมรันไม่มี LLM (ไม่ได้ติดตั้ง Ollama และไม่มี API key) จึงต้องรันด้วย `USE_LLM = False` ซึ่งแปลว่า "คำตอบ" ที่ได้คือการคัดลอกข้อความ chunk อันดับ 1 มาแปะพร้อมต่อท้ายด้วย `[1]`

พอคำตอบคือตัวเอกสารเอง faithfulness ย่อมได้ 1.0 อัตโนมัติ (วัดว่าคำในคำตอบมาจากเอกสารกี่ %) และ has_citation ได้ 1.0 เพราะโค้ดเติม `[1]` ให้เองทุกครั้ง สองค่านี้จึงไม่ได้วัดความสามารถของระบบเลย ไม่ว่าจะใช้คำถามรูปแบบไหน

**ค่าที่เปลี่ยนไปจริงมีสองตัว และเป็นสองตัวที่มีความหมาย** อัตราค้นเจอ chunk ที่ถูกตกจาก 1.0 เหลือ 0.6 ซึ่งอยู่ในระดับเดียวกับ Hit@3 ของ retriever บน `paraphrase` ที่วัดได้ 0.7091 (ต่างกันเพราะไฟล์นี้รันแค่ 20 ข้อแรก ไม่ใช่ทั้ง 55 ข้อ และ `TOP_K = 3`) แปลว่าค่า 1.0 ที่เคยได้คือผลของข้อสอบง่าย ไม่ใช่ความสามารถของระบบ ส่วน correctness ตกจาก 0.98 เหลือ 0.65 เพราะเมื่อค้นผิด chunk ที่หยิบมาก็ไม่ใช่ chunk เดียวกับ reference answer อีกต่อไป

สรุปคือ **สี่ในเจ็ดค่ายังวัดอะไรไม่ได้จนกว่าจะมี LLM** แต่หลังเปลี่ยน variant อย่างน้อยสองค่าที่เหลือก็เริ่มสะท้อนความสามารถจริงของระบบแล้ว

### ระบบเดิมบอกว่า "ไม่รู้" ไม่เป็นเลย

จุดนี้ไม่เกี่ยวกับคะแนน แต่เป็นความสามารถที่ระบบขาดไปทั้งอัน

`config.py` มี `NO_CONTEXT_MESSAGE = "ขออภัย ไม่พบข้อมูลที่เกี่ยวข้อง"` เตรียมไว้ และ `generator.py` ก็มีโค้ดเรียกใช้จริง แต่เงื่อนไขคือ `if not chunks:` ซึ่ง **ไม่มีทางเป็นจริง** เพราะ FAISS คืน top-k ให้เสมอไม่ว่าคำถามจะเกี่ยวข้องหรือไม่ ข้อความนั้นจึงเป็นโค้ดที่ไม่เคยทำงานเลยสักครั้ง

ผลคือระบบตอบทุกคำถามอย่างมั่นใจ พร้อมอ้างอิง `[1]` และ disclaimer ครบ

```
ถาม: วิธีทำส้มตำปูปลาร้าให้อร่อย
     → chunk อันดับ 1 = "ปีกแบบเดลตาให้ข้อดีอะไร"  (คะแนน 0.1348)

ถาม: ราคาหุ้น PTT วันนี้เท่าไร
     → chunk อันดับ 1 = "รถถัง T-72 และรุ่นพัฒนามีลักษณะอย่างไร"  (คะแนน 0.2395)

ถาม: พรุ่งนี้ฝนจะตกไหม
     → chunk อันดับ 1 = "ผลกระทบของการระเบิดนิวเคลียร์มีอะไรบ้าง"  (คะแนน 0.2025)
```

สำหรับระบบที่ขึ้น disclaimer เรื่องข้อมูลอาวุธทุกคำตอบ การตอบมั่วอย่างมั่นใจแบบนี้เป็นปัญหามากกว่าการตอบผิดธรรมดา

**สิ่งที่เพิ่ม** — `MIN_DENSE_SCORE` ใน `config.py` ถ้าคะแนน cosine ที่ดีที่สุดของ chunk ที่ค้นได้ต่ำกว่าค่านี้ pipeline จะส่ง list ว่างให้ `generator` ซึ่งทำให้เงื่อนไข `if not chunks:` ที่โครงร่างเตรียมไว้ทำงานได้จริงเป็นครั้งแรก

ที่ต้องใช้คะแนน dense ไม่ใช่คะแนนรวม เพราะคะแนน RRF คิดจากอันดับล้วน ๆ ค่าจะอยู่ราว 0.03 เท่ากันหมดไม่ว่าคำถามจะตรงแค่ไหน ใช้ตัดสินอะไรไม่ได้

**วิธีวัด** ต้องดูสองด้านพร้อมกัน ([`eval_refusal.py`](RAG-Project/evaluation/eval_refusal.py)) เพราะถ้าดูแต่ "ปฏิเสธถูกกี่ %" ก็แค่ตั้งเกณฑ์สูง ๆ ให้ปฏิเสธทุกอย่างก็ได้ 100% ทันที

คำถามนอกคลัง 19 ข้อเขียนไว้ที่ [`data/out_of_scope.json`](RAG-Project/data/out_of_scope.json) ในนั้นมีสี่ข้อที่ **จงใจใส่คำที่มีอยู่ในคลังจริง** เพื่อดูว่าเกณฑ์ตัดสินจากความหมายหรือแค่จับคำ — "หนังสงครามเรื่องไหนสนุก", "เกมยิงปืนออนไลน์เล่นอะไรดี", "ชุดลายพรางซื้อได้ที่ไหน", "ของเล่นโมเดลรถถังยี่ห้อไหนดี"

| `MIN_DENSE_SCORE` | ปฏิเสธถูก (19 ข้อนอกคลัง) | เผลอปฏิเสธ (55 ข้อในคลัง) |
| :---: | :---: | :---: |
| 0.00 (พฤติกรรมเดิม) | 0.0% | 0.0% |
| 0.30 | 57.9% | 0.0% |
| 0.35 | 73.7% | 0.0% |
| **0.40 (ที่เลือก)** | **73.7%** | **0.0%** |
| 0.45 | 78.9% | 0.0% |
| 0.50 | 84.2% | 7.3% |
| 0.60 | 94.7% | 29.1% |

**สี่ข้อหลอกทำงานได้ผล** ถ้าใช้แต่คำถามนอกคลังแบบง่าย ๆ สองกลุ่มจะแยกขาดกันเลย (นอกคลังสูงสุด 0.3480 ในคลังต่ำสุด 0.4573) ผมเกือบสรุปไปแล้วว่าตั้งเกณฑ์แล้วแยกได้ 100% แต่พอใส่ข้อหลอกเข้าไป **สองกลุ่มคาบเกี่ยวกัน 0.1477** — "เกมยิงปืนออนไลน์ตอนนี้เล่นอะไรดี" ได้ 0.6050 ซึ่งสูงกว่าคำถามจริง 26 ข้อ

แปลว่าโมเดลจับได้แค่ว่า "ประโยคนี้พูดเรื่องอาวุธ" แต่แยกไม่ออกว่าเป็นการถามความรู้หรือถามหาเกม

**ทำไมเลือก 0.40 ทั้งที่ 0.45 ดีกว่า** — 0.45 ปฏิเสธถูกมากกว่า 5% โดยยังไม่เผลอปฏิเสธเลย ดูเหมือนเลือกง่าย แต่มันห่างจากคำถามในคลังที่คะแนนต่ำสุด (0.4573) แค่ **0.0073** คือเกาะขอบข้อมูลที่วัดพอดีเป๊ะ คำถามใหม่ข้อเดียวที่คะแนนต่ำกว่านั้นก็พังทันที ผมเลือก 0.40 เพื่อให้มีระยะเผื่อ ยอมแลกกับคำถามนอกคลังที่หลุดมาเพิ่ม 1 ข้อ

ผลสุทธิคือระบบปฏิเสธคำถามนอกเรื่องได้ราวสามในสี่ โดยยังไม่ปฏิเสธคำถามที่ตอบได้เลยสักข้อ จาก 0% เดิม

| สิ่งที่ตั้งใจจะทำ | ผลที่ได้จริง |
| :--- | :--- |

นอกจากสี่ข้อนั้น ระหว่างทางยังเจอของที่ไม่ได้อยู่ในแผนอีกสองอย่าง

| `eval_generation.py` วัดด้วย variant ที่ง่ายที่สุด และหัวไฟล์ก๊อปมาจากไฟล์อื่น | เปลี่ยนมาใช้ `paraphrase` — อัตราค้นเจอ chunk ที่ถูกตกจาก 1.0 เหลือ 0.6 |

### ย้อนไปดูสิ่งที่เขียนค้างไว้ตอน LAB02

ตอนจบ LAB02 ผมเขียนไว้ท้าย README ว่ามีห้าเรื่องที่ควรทำต่อ พอมาถึงใบงานนี้เลยลองไล่ดูว่าทำไปได้กี่ข้อ

| ที่เขียนไว้ตอน LAB02 | ในใบงานนี้ |
| :--- | :--- |
| ผสม BM25 เข้ากับ semantic search | ทำแล้ว เป็นหัวข้อหลักของใบงานนี้พอดี |
| มี score threshold ตัดผลที่ไม่มั่นใจทิ้ง ดีกว่าตอบผิดแบบมั่นใจ | ทำแล้ว คือ `MIN_DENSE_SCORE` |
| ลองโมเดล embedding ตัวอื่น | ทำแล้ว เทียบกับ `multilingual-e5-small` |
| reranker แบบ cross-encoder | ยังไม่ได้ทำ ติดที่ยังไม่ได้โหลดโมเดล |
| กรองด้วย `category` ก่อนค้น | ยังไม่ได้ทำ ทั้งที่ทุก chunk ยังเก็บ `category` ไว้อยู่ |

มีสองเรื่องที่น่าบันทึกไว้

เรื่องแรกคือประโยค "ดีกว่าตอบผิดแบบมั่นใจ" ที่เขียนไว้ตอน LAB02 กลายเป็นเหตุผลเดียวกันกับที่ทำให้เพิ่ม `MIN_DENSE_SCORE` ในใบงานนี้ ตอนนั้นเจอปัญหาจากการดูผลด้วยตาแค่ 5 ข้อ คราวนี้เจอซ้ำแต่วัดออกมาเป็นตัวเลขได้

เรื่องที่สองคืออาการ hub vector ตอน LAB02 ผมเดาว่าเป็นเพราะโมเดลเล็กแค่ 384 มิติ พอมาเทียบจริงในใบงานนี้ `multilingual-e5-small` ที่เป็น 384 มิติเท่ากันกลับแก้อาการนี้ได้ **ที่เดาไว้จึงถูกครึ่งเดียว** ปัญหาไม่ได้อยู่ที่จำนวนมิติ แต่อยู่ที่โมเดลถูกเทรนมาเพื่องานอะไร

### จะทำต่อยังไง

เรื่องที่ค้างอยู่จริง ๆ ตอนนี้เหลือสามเรื่อง

**หนึ่ง — หา LLM มาต่อให้ได้** เป็นตัวขวางที่ใหญ่ที่สุด เพราะปิดทั้งการวัดคุณภาพคำตอบ, query transformation ทั้งสามโหมด และ memory ไว้พร้อมกัน ทั้งหมดเขียนโค้ดครบแล้วแต่ยังพิสูจน์ไม่ได้ว่าช่วยจริงหรือไม่

**สอง — เกณฑ์ปฏิเสธยังหลอกได้ด้วยคำถามที่ "พูดเรื่องอาวุธแต่ไม่ได้ถามความรู้"** เช่น ถามหาเกมยิงปืนหรือหนังสงคราม คะแนน cosine อย่างเดียวแยกไม่ออก ทางที่ควรลองคือดูว่ารูปประโยคเป็นการถามข้อเท็จจริงหรือไม่ ซึ่งถ้ามี LLM ก็ให้มันช่วยตัดสินได้ตรง ๆ

**สาม — ขยาย paraphrase ให้ครบ 120 ข้อ** ตอนนี้มี 55 ข้อ ซึ่งน้อยเกินกว่าจะแยกส่วนต่างระดับ 1% ได้ (เห็นชัดตอนลองค่า RRF) ถ้าครบทุกข้อจะเริ่มเชื่อตัวเลขย่อยรายหมวดได้ด้วย และควรแยกชุดสำหรับปรับค่ากับชุดสำหรับวัดผลออกจากกัน ไม่ใช้ชุดเดียวทำสองหน้าที่แบบตอนนี้

**สี่ — เอา `category` มาใช้สักที** ทุก chunk เก็บหมวดไว้ตั้งแต่ LAB02 แล้วยังไม่เคยถูกใช้กรองอะไรเลยทั้งสองใบงาน แนวที่น่าลองคือให้ระบบเดาหมวดของคำถามก่อน แล้วค่อยค้นเฉพาะในหมวดนั้น หรือใช้เป็นตัวถ่วงน้ำหนักตอนจัดอันดับ น่าจะช่วยกับเคสที่หยิบ chunk ข้ามหมวดมาผิด ซึ่งเป็นรูปแบบความผิดพลาดที่เจอบ่อยที่สุดในทั้งสองใบงาน

**ห้า — ถ้าจะใช้งานจริงควรเปลี่ยนไป e5-small และรันชุดวัดผลใหม่ทั้งหมด** ตอนนี้ผมคงค่าเริ่มต้นไว้ที่ MiniLM เพื่อให้ตารางเทียบกับรอบก่อนได้ แต่ถ้าจะเดินต่อจริงควรตัดสินใจเปลี่ยนแล้วรันใหม่ทั้งชุด พร้อมกับดูว่า `SLANG_MAP` ยังจำเป็นอยู่ไหม เพราะ e5 ทำ `slang` ได้เต็มโดยไม่ต้องใช้ตาราง

### แหล่งตรวจสอบข้อเท็จจริงใน dataset

ข้อความทั้ง 361 คู่เขียนขึ้นใหม่สำหรับใบงานนี้ ไม่ได้คัดลอกประโยคจากที่ใด แต่**ข้อเท็จจริงในนั้นไม่ใช่ของใหม่** — มีคำตอบ 79 ข้อที่ระบุปี ขนาดกระสุน ระยะ หรือชื่อรุ่นแบบเจาะจง ซึ่งเป็นความรู้มาตรฐานในโดเมนและต้องตรวจสอบย้อนกลับได้

ตารางนี้จึงบอกว่า **แต่ละหมวดตรวจสอบข้อเท็จจริงได้จากที่ไหน** ไม่ใช่รายการที่คัดลอกข้อความมา

ไม่มีการใช้ข้อมูลที่ละเมิดลิขสิทธิ์ ข้อมูลส่วนบุคคลที่ไม่ได้รับอนุญาต หรือข้อมูลผิดกฎหมาย เนื้อหาเป็นความรู้เชิงสารานุกรมที่เผยแพร่ทั่วไป เรียบเรียงเพื่อการศึกษา ไม่มีข้อมูลเชิงปฏิบัติการหรือวิธีสร้าง/ดัดแปลงอาวุธ
